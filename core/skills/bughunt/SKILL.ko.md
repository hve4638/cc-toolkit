# 버그 진단

어려운 버그를 위한 디시플린. 단계 생략은 명시적으로 정당화될 때만 한다.

## Phase 1 — 피드백 루프 구축

**이것이 이 스킬의 전부다.** 나머지는 기계적인 작업이다. 버그에 대한 **타이트한** pass/fail 신호 — _이_ 버그에 빨간불이 켜지는 신호 — 가 있으면 원인은 찾게 된다; bisection, 가설 검증, 계측은 모두 그 신호를 소비할 뿐이다. 신호가 없으면 코드를 아무리 들여다봐도 소용없다.

여기에 불균형할 만큼 많은 노력을 쏟는다. **공격적으로. 창의적으로. 포기하지 말 것.**

### 루프를 만드는 방법 — 대략 이 순서로 시도한다

1. **실패하는 테스트** — 버그에 닿는 아무 seam에서든: unit, integration, e2e.
2. **Curl / HTTP 스크립트** — 실행 중인 dev 서버 대상.
3. **CLI 실행** — fixture 입력을 주고 stdout을 known-good 스냅샷과 diff.
4. **헤드리스 브라우저 스크립트** (Playwright / Puppeteer) — UI를 조작하고 DOM/console/network에 대해 assert.
5. **캡처한 트레이스 재생.** 실제 네트워크 요청/페이로드/이벤트 로그를 디스크에 저장해 두고, 격리된 코드 경로로 재생한다.
6. **일회용 하네스.** 시스템의 최소 부분집합(서비스 하나, 의존성 mock)을 띄워 버그 코드 경로를 함수 호출 한 번으로 실행한다.
7. **Property / fuzz 루프.** "가끔 출력이 틀린다"류 버그면 무작위 입력 1000개를 돌려 실패 모드를 찾는다.
8. **Bisection 하네스.** 두 known 상태(커밋, 데이터셋, 버전) 사이에서 생긴 버그면 "상태 X로 부팅, 확인, 반복"을 자동화해 `git bisect run`이 가능하게 만든다.
9. **Differential 루프.** 같은 입력을 구버전 vs 신버전(또는 두 config)에 돌려 출력을 diff 한다.
10. **HITL bash 스크립트.** 최후 수단. 사람이 클릭해야만 한다면 `scripts/hitl-loop.template.sh`로 그 사람을 구동해 루프의 구조를 유지한다. 캡처된 출력은 다시 에이전트에게 돌아온다.

올바른 피드백 루프를 만들면 버그는 90% 잡힌 것이다.

### 루프 조이기

루프를 제품처럼 다룬다. 일단 루프가 생기면 **조인다**:

- 더 빠르게 만들 수 있나? (셋업 캐시, 무관한 init 생략, 테스트 범위 축소.)
- 신호를 더 날카롭게 만들 수 있나? ("크래시 안 남"이 아니라 구체적 증상에 대해 assert.)
- 더 결정적으로 만들 수 있나? (시간 고정, RNG 시드, 파일시스템 격리, 네트워크 동결.)

30초짜리 flaky 루프는 루프 없는 것보다 조금 나을 뿐이다; 2초짜리 결정적 루프가 타이트한 루프다 — 디버깅의 초능력.

### 비결정적 버그

목표는 깨끗한 재현이 아니라 **더 높은 재현율**이다. 트리거를 100번 반복하고, 병렬화하고, 부하를 더하고, 타이밍 윈도를 좁히고, sleep을 주입한다. 50% flake는 디버깅 가능하다; 1%는 불가능하다 — 디버깅 가능해질 때까지 재현율을 끌어올린다.

### 정말로 루프를 만들 수 없을 때

멈추고 명시적으로 말한다. 시도한 것들을 나열한다. 사용자에게 요청한다: (a) 재현되는 환경에의 접근, (b) 캡처된 아티팩트(HAR 파일, 로그 덤프, 코어 덤프, 타임스탬프 있는 화면 녹화), (c) 임시 프로덕션 계측 허가. 루프 없이 가설 단계로 진행하지 **않는다**.

### 완료 기준 — 빨간불이 켜지는 타이트한 루프

Phase 1은 루프가 **타이트**하고 **빨간불을 켤 수 있을** 때 끝난다: **명령 하나** — 스크립트 경로, 테스트 실행, curl — 를 댈 수 있고, 그것을 **이미 한 번 이상 실행했으며**(호출과 출력을 붙여넣는다), 다음을 만족한다:

- [ ] **Red-capable** — 실제 버그 코드 경로를 구동하고 **사용자의 정확한 증상**에 대해 assert 한다. 그래서 이 버그에 빨간불이, 고치면 초록불이 켜진다. "에러 없이 돌아감"이 아니다 — _이 특정 버그를 잡을 수 있어야_ 한다.
- [ ] **결정적** — 매 실행 같은 판정 (flaky 버그: 위에 따라 고정된 높은 재현율).
- [ ] **빠름** — 분이 아니라 초 단위.
- [ ] **에이전트가 실행 가능** — 사람 없이 실행할 수 있다; human in the loop은 `scripts/hitl-loop.template.sh`를 통해서만.

이 명령이 존재하기 전에 이론을 세우려고 코드를 읽고 있다면, **멈춘다 — 가설로 직행하는 것이 바로 이 스킬이 막는 실패다.** red-capable 명령 없이는 Phase 2도 없다.

## Phase 2 — 재현 + 최소화

루프를 돌린다. 빨간불이 켜지는 것을 관찰한다 — 버그가 나타난다.

확인:

- [ ] 루프가 **사용자**가 묘사한 실패 모드를 낸다 — 근처에 있는 다른 실패가 아니라. 다른 버그 = 다른 수정.
- [ ] 실패가 여러 실행에 걸쳐 재현된다 (비결정적 버그면 디버깅에 충분한 재현율로).
- [ ] 정확한 증상(에러 메시지, 잘못된 출력, 느린 타이밍)을 캡처해 뒀다 — 이후 단계에서 수정이 실제로 그 증상을 해결했는지 검증할 수 있도록.

### 최소화

빨간불이 켜지면, 재현을 **여전히 빨간불이 켜지는 가장 작은 시나리오**로 줄인다. 입력, 호출자, config, 데이터, 단계를 **하나씩** 잘라내며 매번 루프를 다시 돌린다 — 실패에 하중을 받는 것만 남긴다.

이유: 최소 재현은 Phase 3의 가설 공간을 줄이고(의심할 부품이 줄어든다), Phase 5의 깨끗한 회귀 테스트가 된다.

**남은 모든 요소가 하중을 받을 때** 완료다 — 어느 하나를 제거해도 루프가 초록불이 된다.

재현 **및** 최소화 전에는 진행하지 않는다.

## Phase 3 — 가설

테스트하기 전에 **순위를 매긴 가설 3–5개**를 생성한다. 가설을 하나만 만들면 첫 그럴듯한 아이디어에 앵커링된다.

각 가설은 **반증 가능**해야 한다: 그 가설이 하는 예측을 명시한다.

> 형식: "<X>가 원인이면, <Y를 바꾸면> 버그가 사라진다 / <Z를 바꾸면> 악화된다."

예측을 말할 수 없으면 그 가설은 vibe다 — 버리거나 날카롭게 다듬는다.

**테스트 전에 순위 목록을 사용자에게 보여준다.** 사용자는 종종 순위를 즉시 바꾸는 도메인 지식("#3 관련 변경을 방금 배포했다")이나 이미 배제한 가설을 알고 있다. 저렴한 체크포인트, 큰 시간 절약. 사용자가 자리에 없으면 막히지 말고 자신의 순위대로 진행한다.

## Phase 4 — 계측

각 probe는 Phase 3의 특정 예측에 대응해야 한다. **한 번에 변수 하나만 바꾼다.**

도구 우선순위:

1. 환경이 지원하면 **디버거 / REPL 검사**. breakpoint 하나가 로그 열 개를 이긴다.
2. 가설을 구별하는 경계에 놓는 **표적 로그**.
3. "전부 로그 찍고 grep"은 절대 하지 않는다.

**모든 디버그 로그에 고유 prefix 태그를 단다**, 예: `[DEBUG-a4f2]`. 마지막 정리가 grep 한 번이 된다. 태그 없는 로그는 살아남고; 태그 있는 로그는 죽는다.

**Perf 분기.** 성능 회귀에는 로그가 대개 틀린 도구다. 대신: 기준 측정을 세우고(타이밍 하네스, `performance.now()`, 프로파일러, 쿼리 플랜), bisect 한다. 먼저 측정, 그다음 수정.

## Phase 5 — 수정 + 회귀 테스트

수정 **전에** 회귀 테스트를 쓴다 — 단, **올바른 seam**이 있을 때만.

올바른 seam이란 테스트가 호출 지점에서 발생하는 그대로의 **실제 버그 패턴**을 실행하는 곳이다. 가용한 seam이 너무 얕으면(버그에는 호출자 여럿이 필요한데 단일 호출자 테스트뿐, 버그를 유발한 체인을 재현할 수 없는 unit 테스트뿐) 거기 놓인 회귀 테스트는 거짓 자신감을 준다.

**올바른 seam이 없다면, 그것 자체가 발견이다.** 기록한다. 코드베이스 아키텍처가 버그를 잠그지 못하게 막고 있는 것이다. 다음 단계를 위해 표시해 둔다.

올바른 seam이 있으면:

1. 최소화된 재현을 그 seam의 실패하는 테스트로 바꾼다.
2. 실패를 관찰한다.
3. 수정을 적용한다.
4. 통과를 관찰한다.
5. 원래(최소화 전) 시나리오에 대해 Phase 1 피드백 루프를 다시 돌린다.

## Phase 6 — 정리 + 포스트모템

완료 선언 전 필수:

- [ ] 원래 재현이 더 이상 재현되지 않는다 (Phase 1 루프 재실행)
- [ ] 회귀 테스트 통과 (또는 seam 부재가 문서화됨)
- [ ] 모든 `[DEBUG-...]` 계측 제거 (prefix를 `grep`)
- [ ] 일회용 프로토타입 삭제 (또는 명확히 표시된 debug 위치로 이동)
- [ ] 맞았던 것으로 판명된 가설을 커밋/PR 메시지에 기술 — 다음 디버거가 배우도록

**그리고 묻는다: 무엇이 이 버그를 막을 수 있었나?** 답이 아키텍처 변경(좋은 테스트 seam 없음, 얽힌 호출자, 숨은 결합)을 수반하면 구체 내용을 사용자에게 보고한다. 권고는 수정이 들어간 **후에** 한다, 전이 아니라 — 시작할 때보다 지금 더 많은 정보를 갖고 있다.
