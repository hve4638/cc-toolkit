# showcase VISION

이 문서는 showcase 의 의도를 기록한다. 무엇을 만들려 했고, 왜 필요하며, 무엇은 일부러 하지 않기로 했는가. 구현이 진행되어도 갱신하지 않고 그대로 얼려 둔다. 나중에 나온 제안이 이 방향에서 벗어나거나 목적을 넘어설 때, 그 제안을 이 문서에 비춰 판단하기 위한 앵커다. 현재 진행 상태·규칙·계획은 다른 곳(PLAN, 스펙, 코드)에 있고, 여기에는 왜·무엇·무엇은 아닌지만 담는다. 이 판은 2026-07-13 의 데모 산출물 중심 재정의를 기록한 것이며, 이전 판들(모듈 프레이밍, 체크포인트 시퀀스)은 git 히스토리에 남아 있다. 2026-07-15 스킬명이 showcase 에서 demo-first 로 개명되고 사용자 명시 호출 전용(disable-model-invocation)이 되었다; 아래 본문의 showcase 표기는 개명 전 기록 그대로 둔다.

## 무엇인가

showcase 는 큰 규모의 코딩 작업을 `demo/` 아래 개별 실행 가능한 데모들로 만들어 진행하는 작업 규율이다. 데모 하나는 그 시점에 해소할 불확실성 하나 — 사람이 직접 만들었다면 다음으로 확인했을 질문 — 에 답한다. 훅이 발화해 CLI 에 닿는가, 실제 전송으로 A→서버→B 가 중계되는가 같은 것이다. 데모 폴더 하나가 자체로 시연되고, 사용자는 데모를 돌려보며 작업의 맥락을 따라간다.

데모는 보여주기용 목업이 아니다. 질문에 답하는 핵심 경로는 제품에서 쓸 실물로 구현하고, 깡통은 주변부에만 허용한다. 그래서 통과한 데모의 핵심 코드는 제품 코드의 씨앗이 되고, 확인이 곧 제품의 전진이 된다.

이 판은 실사용 세션(project-amux 의 데모 기반 개발, 2026-07-13)에서 검증된 형태를 기록한다. 이전 판이 상정했던 체크포인트 루프(목록 선제시 후 체크포인트마다 정지·관찰 대기)는 실전에서 옵트아웃되었고, 상시 주입 가드레일(`.showcase` 마커, SessionStart 훅)도 함께 은퇴했다. showcase 는 명시 호출 스킬이며, 세션을 넘는 지속성은 demo/ 산출물(폴더, README, last-pass 해시)이 담당한다.

## 왜 / 목표

에이전트에 의존한 코딩의 산출물은 표면만 보고는 신뢰하기 어렵다. 산출물이 클수록 더 그렇다. showcase 는 이 신뢰 격차를 사용자 쪽에서 메운다.

- 사람이 직접 만들었다면 확인했을 것을 그 순서대로, 직접 돌려볼 수 있는 데모로 확인시킨다. 설명이 아니라 실행으로 신뢰가 생긴다.
- 핵심을 실물로 강제해, 데모 확인이 장식이 아니라 제품의 실제 전진과 일치하게 한다.

## 하지 않는 것

- 정확성 보증이 아니다. 데모가 건드리지 않은 경로의 결함은 남을 수 있고, showcase 는 그것을 주장하지 않는다.
- 프로젝트 전체의 유닛테스트·CI·커버리지 정책에 관여하지 않는다. 데모 폴더가 자체 검증 테스트를 품는 것은 그 데모의 일부일 뿐, 프로젝트의 기계 검증 층은 별도다.
- 구현 구조를 처방하지 않는다. 데모는 확인의 단위이지 코드를 조직하는 방식이 아니다.
- 진행 절차를 강제하지 않는다. 이전 판의 체크포인트마다 정지·관찰 대기는 은퇴했다. 데모가 실행 가능해지는 대로 제시하고, 속도는 사용자가 조절한다. 승인 게이트가 아니다.
- 상시 가드레일이 아니다. 마커·훅 주입 없이 명시 호출로만 쓴다.
- inlay 를 대체하거나 그 위에 얹히지 않는다. inlay 는 에이전트에게 컨텍스트를 주는 내부용 층이고, showcase 는 사용자에게 확신을 주는 외부용 층이다.

## 전제

- 신뢰는 표면 훑기가 아니라, 자기가 궁금하던 질문의 답을 직접 실행·관찰할 때 생긴다. 확인의 단위는 코드가 아니라 질문이다.
- 핵심이 깡통인 데모는 확인해도 제품이 전진하지 않는다. 핵심이 실물이어야 데모 통과가 곧 채택 판정이자 제품의 씨앗이 된다.
- 산출물이 맥락을 운반한다. 폴더·실행 명령·last-pass 해시가 남아 있으면, 마커나 상시 주입 없이도 다음 세션과 사용자가 맥락을 이어받는다.

## 시나리오

- 훅 수집 시스템이라면: demo/hook-echo (훅이 발화해 raw JSON 이 CLI 에 흐르는가) → demo/starmesh-relay (실제 전송 라이브러리로 A→서버→B 가 중계되는가; 채택 판정 게이트) → demo/raw-pipeline (둘이 이어지는가) → … 처럼 demo/ 폴더가 쌓인다.
- 독립인 데모들은 서브에이전트가 병렬로 작성할 수 있다. 각 데모의 완료 기준에 자체 테스트 통과와 README 기록을 박는다.
- 채택 판정 데모가 후보의 부적합을 드러내면, 우회로 덮지 않고 부적합 판정을 기록하는 것으로 완료한다.

## 열어 둔 것

- 통과한 데모의 핵심 코드를 제품으로 이식(승격)하는 절차를 규약화할지.
- 실물로 교체된 뒤의 옛 데모를 계속 유지할지 은퇴시킬지.
- 재사용 가능한 데모 스캐폴딩·도구를 제공할지.
