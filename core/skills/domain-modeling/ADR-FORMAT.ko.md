# ADR 형식

ADR 은 `docs/adr/` 에 살고 순차 번호를 쓴다: `0001-slug.md`, `0002-slug.md`, 이런 식.

`docs/adr/` 디렉터리는 lazy 하게 만든다 — 첫 ADR 이 필요할 때만.

## 템플릿

```md
# {Short title of the decision}

{1-3 sentences: what's the context, what did we decide, and why.}
```

이게 전부다. ADR 은 한 문단이어도 된다. 가치는 결정이 내려졌다는 *사실*과 그 *이유*를 남기는 데 있지, 칸을 채우는 데 있지 않다.

## 선택 절

진짜 가치를 더할 때만 넣는다. 대부분의 ADR 에는 필요 없다.

- **Status** frontmatter (`proposed | accepted | deprecated | superseded by ADR-NNNN`) — 결정을 다시 들여다보게 될 때 유용하다
- **Considered Options** — 기각한 대안이 기억할 가치가 있을 때만
- **Consequences** — 자명하지 않은 하류 영향을 짚어야 할 때만

## 번호

`docs/adr/` 를 훑어 가장 큰 번호를 찾고 1을 더한다.

## 언제 ADR 을 제안하나

다음 셋이 모두 참이어야 한다:

1. **되돌리기 어렵다** — 나중에 마음을 바꾸는 비용이 유의미하다
2. **맥락 없이는 의아하다** — 나중의 독자가 코드를 보고 "대체 왜 이렇게 했지?" 하고 궁금해할 것이다
3. **진짜 트레이드오프의 결과다** — 실제 대안들이 있었고 구체적인 이유로 하나를 골랐다

되돌리기 쉬운 결정이면 건너뛴다 — 그냥 되돌리면 된다. 의아하지 않으면 아무도 이유를 궁금해하지 않는다. 진짜 대안이 없었다면 "당연한 것을 했다" 외에 기록할 게 없다.

### 무엇이 자격이 있나

- **아키텍처의 형태.** "우리는 모노레포를 쓴다." "쓰기 모델은 event-sourced 이고, 읽기 모델은 Postgres 로 projection 된다."
- **컨텍스트 간 통합 패턴.** "Ordering 과 Billing 은 동기 HTTP 가 아니라 도메인 이벤트로 통신한다."
- **락인을 동반하는 기술 선택.** 데이터베이스, 메시지 버스, 인증 제공자, 배포 대상. 모든 라이브러리가 아니라, 갈아치우는 데 한 분기가 걸릴 것들만.
- **경계와 범위 결정.** "Customer 데이터는 Customer 컨텍스트가 소유하고, 다른 컨텍스트는 ID 로만 참조한다." 명시적인 '아니오' 는 '예' 만큼 가치 있다.
- **뻔한 길에서 의도적으로 벗어난 것.** "X 때문에 ORM 대신 수동 SQL 을 쓴다." 합리적인 독자라면 반대를 가정할 만한 모든 것. 이것이 다음 엔지니어가 의도된 것을 "고치는" 일을 막는다.
- **코드에 보이지 않는 제약.** "컴플라이언스 요구 때문에 AWS 를 쓸 수 없다." "파트너 API 계약 때문에 응답 시간이 200ms 미만이어야 한다."
- **기각이 자명하지 않은 기각된 대안.** GraphQL 을 검토하고 미묘한 이유로 REST 를 골랐다면 기록한다 — 안 그러면 반년 뒤 누군가 GraphQL 을 다시 제안한다.
