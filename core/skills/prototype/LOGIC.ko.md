# Logic 프로토타입

사용자가 상태 모델을 손으로 조작해 보는 작은 인터랙티브 터미널 앱. 질문이 **비즈니스 로직, 상태 전이, 데이터 형태**에 관한 것일 때 쓴다 — 종이 위에서는 그럴듯해 보이지만 실제 케이스로 밀어붙여야 비로소 어긋남이 느껴지는 종류.

## 이 형태가 맞는 경우

- "X 다음 Y 가 오는 엣지 케이스를 이 상태 머신이 처리하는지 모르겠다."
- "이 데이터 모델로 ... 인 경우를 정말 표현할 수 있나."
- "실제로 작성하기 전에 API 가 어떤 모양이어야 할지 감을 잡고 싶다."
- 사용자가 **버튼을 누르며 상태가 변하는 것을 지켜보고** 싶어하는 모든 경우.

질문이 "이게 어떻게 생겨야 하나" 라면 — 분기가 틀렸다. [UI.ko.md](UI.ko.md) 를 쓴다.

## 절차

### 1. 질문을 명시한다

코드를 쓰기 전에, 어떤 상태 모델과 어떤 질문을 프로토타이핑하는지 적는다. 한 문단, 프로토타입의 README 나 파일 상단 주석에. 엉뚱한 질문에 답하는 logic 프로토타입은 순수한 낭비다 — 질문을 명시해 두면 나중에 검증할 수 있다, 사용자가 지금 지켜보고 있든 자리를 비웠다 돌아오든.

### 2. 언어를 고른다

호스트 프로젝트가 쓰는 것을 쓴다. 프로젝트에 명확한 런타임이 없으면 (예: docs 저장소) 물어본다.

툴링은 프로젝트의 기존 컨벤션을 따른다 — 프로토타입 하나를 위해 새 패키지 매니저나 런타임을 추가하지 않는다.

### 3. 로직을 이식 가능한 모듈로 격리한다

실제 로직 — 질문에 답하는 그 부분 — 을 작고 순수한 인터페이스 뒤에 둔다. 나중에 들어내서 실제 코드베이스에 떨어뜨릴 수 있는 형태로. 주변의 TUI 는 throwaway 지만, 로직 모듈은 아니어야 한다.

맞는 형태는 질문에 따라 다르다:

- **순수 reducer** — `(state, action) => state`. 액션이 이산적 이벤트이고 상태가 단일 값일 때 좋다.
- **상태 머신** — 명시적 상태와 전이. "지금 어떤 액션이 애초에 합법인가" 자체가 질문의 일부일 때 좋다.
- 평범한 데이터 타입 위의 **작은 순수 함수 집합**. 암묵적 현재 상태가 없고 변환만 있을 때 좋다.
- 로직이 정말로 지속적인 내부 상태를 소유할 때는 **명확한 메서드 표면을 가진 클래스나 모듈**.

TUI 에 연결하기 쉬운 형태가 아니라, *묻고 있는 질문에 가장 맞는* 형태를 고른다. 순수하게 유지한다: I/O 없음, 터미널 코드 없음, 제어 흐름용 `console.log` 없음. TUI 가 모듈을 import 해 호출한다; 반대 방향으로는 아무것도 흐르지 않는다.

이것이 프로토타입을 제 수명 너머까지 유용하게 만든다: 질문에 답이 나오면, 검증된 reducer / 머신 / 함수 집합만 따로 실제 모듈로 들어올릴 수 있다.

### 4. 상태를 노출하는 최소한의 TUI 를 만든다

**경량 TUI** 로 만든다 — 매 틱마다 화면을 지우고 (`console.clear()` / `print("\033[2J\033[H")` / 상당물) 프레임 전체를 다시 그린다. 사용자에게는 항상 하나의 안정된 화면이 보여야 한다, 끝없이 자라는 스크롤백이 아니라.

각 프레임은 두 부분, 이 순서로:

1. **현재 상태**, 보기 좋게 diff 하기 쉽게 출력 (한 줄에 필드 하나, 또는 포맷된 JSON). 필드명·섹션 헤더에 **bold**, 덜 중요한 맥락 (타임스탬프, ID, 파생 값) 에 **dim**. 네이티브 ANSI 이스케이프 코드면 충분하다 — `\x1b[1m` bold, `\x1b[2m` dim, `\x1b[0m` reset. 프로젝트에 이미 있지 않은 한 스타일링 라이브러리를 끌어올 필요 없다.
2. **키보드 단축키**, 하단에 나열: `[a] add user  [d] delete user  [t] tick clock  [q] quit`. 키를 bold 로, 설명을 dim 으로, 또는 그 반대 — 깔끔하게 읽히는 쪽으로.

동작:

1. **상태 초기화** — 단일 인메모리 객체/구조체. 시작 시 첫 프레임을 렌더링한다.
2. **키 입력 하나 (또는 한 줄) 씩 읽어** 상태를 변경하는 핸들러로 디스패치한다.
3. 모든 액션 후 프레임 전체를 **다시 그린다** — 덧붙이지 말고 교체한다.
4. **종료할 때까지 루프.**

프레임 전체가 한 화면에 들어와야 한다.

### 5. 한 명령으로 실행 가능하게 한다

프로젝트의 기존 task runner (`package.json` scripts, `Makefile`, `justfile`, `pyproject.toml`) 에 스크립트를 추가한다. 사용자는 `pnpm run <prototype-name>` 이나 상당물을 실행하면 된다 — 경로를 기억할 필요가 없어야 한다.

호스트 프로젝트에 task runner 가 없으면, 프로토타입 README 상단에 명령만 적어 둔다.

### 6. 넘겨준다

사용자에게 실행 명령을 준다. 직접 조작하는 건 사용자다; 흥미로운 순간은 "잠깐, 이게 가능하면 안 되는데" 나 "어, X 는 다를 줄 알았는데" 라고 말할 때다 — 그것이 _아이디어_ 의 버그이고, 그게 요점 전부다. 새 액션을 원하면 추가한다. 프로토타입은 진화한다.

### 7. 답과 프로토타입을 캡처한다

프로토타입이 질문에 답했으면, 답을 캡처하고, 프로토타입은 [SKILL](SKILL.ko.md) 이 기술하는 방식으로 캡처한다. logic 특유의 대응: 검증된 reducer / 머신 / 함수 집합은 실제 모듈로 들어올린다 (결정의 흡수); TUI 셸은 프로토타입을 1차 사료로 보존하는 throwaway 브랜치에 함께 실려 간다.

## 안티패턴

- **테스트를 추가하지 않는다.** 테스트가 필요한 프로토타입은 더 이상 프로토타입이 아니다.
- **실제 데이터베이스에 연결하지 않는다.** 질문이 명시적으로 영속화에 관한 것이 아닌 한 인메모리 스토어를 쓴다.
- **일반화하지 않는다.** "나중에 X 를 지원하고 싶어지면" 은 없다. 프로토타입은 하나의 질문에 답한다.
- **로직과 TUI 를 뒤섞지 않는다.** reducer / 상태 머신이 `console.log`, 프롬프트, 터미널 이스케이프 코드를 참조하면 더 이상 이식 가능하지 않다. TUI 는 순수 모듈 위의 얇은 셸로 유지한다.
- **TUI 셸을 프로덕션에 싣지 않는다.** 셸은 터미널에서 손으로 조작하는 데 최적화돼 있다. 그 뒤의 로직 모듈이 간직할 가치가 있는 부분이다.
