# Prototype

프로토타입은 **질문에 답하는 throwaway 코드**다. 질문이 형태를 결정한다.

## 분기 선택

어느 질문에 답하는지 식별한다 — 사용자의 프롬프트, 주변 코드에서, 또는 사용자가 있다면 물어서:

- **"이 로직 / 상태 모델이 맞는 느낌인가?"** → [LOGIC.ko.md](LOGIC.ko.md). 종이 위에서는 따지기 어려운 케이스로 상태 머신을 밀어붙이는 작은 인터랙티브 터미널 앱을 만든다.
- **"이게 어떻게 생겨야 하나?"** → [UI.ko.md](UI.ko.md). 한 라우트 위에 급진적으로 다른 UI 변형 여러 개를 만들고, URL 검색 파라미터와 플로팅 하단 바로 전환한다.

두 분기의 산출물은 완전히 다르다 — 여기서 틀리면 프로토타입 전체가 낭비다. 질문이 정말로 모호하고 사용자에게 물을 수 없다면, 주변 코드에 더 맞는 분기를 기본으로 삼고 (백엔드 모듈 → logic, 페이지·컴포넌트 → UI) 그 가정을 프로토타입 상단에 명시한다.

## 두 분기 공통 규칙

1. **첫날부터 throwaway이며, 그렇게 명확히 표시한다.** 프로토타입 코드는 실제로 쓰일 곳 가까이에 둔다 (프로토타이핑 대상 모듈이나 페이지 옆) — 맥락이 자명하도록. 단, 지나가던 독자도 프로덕션이 아니라 프로토타입임을 알 수 있게 이름 짓는다. throwaway UI 라우트는 프로젝트의 기존 라우팅 컨벤션을 따른다; 새 최상위 구조를 발명하지 않는다.
2. **한 명령으로 실행.** 프로젝트의 기존 task runner가 지원하는 무엇이든 — `pnpm <name>`, `python <path>`, `bun <path>` 등. 사용자가 고민 없이 시작할 수 있어야 한다.
3. **기본적으로 영속화 없음.** 상태는 메모리에 산다. 영속화는 프로토타입이 _검사하는_ 대상이지, 의존할 대상이 아니다. 질문이 명시적으로 데이터베이스를 포함하면, 스크래치 DB 나 "PROTOTYPE — wipe me" 가 분명한 이름의 로컬 파일을 쓴다.
4. **다듬기 생략.** 테스트 없음, 프로토타입을 _실행 가능하게_ 만드는 수준을 넘는 에러 처리 없음, 추상화 없음. 요점은 빠르게 배우는 것이다.
5. **상태를 표면화한다.** 모든 액션 후 (logic) 또는 모든 변형 전환 시 (UI), 관련 상태 전체를 출력하거나 렌더링해 사용자가 무엇이 바뀌었는지 볼 수 있게 한다.
6. **끝나면 캡처한다.** 검증된 결정을 실제 코드에 반영한 뒤, 프로토타입 자체를 **1차 사료**로 캡처한다: main 밖 throwaway 브랜치에 커밋한다. 답도 캡처한다 — 판정과 그것이 해소한 질문, 그리고 그 브랜치를 가리키는 포인터 — 프로젝트가 결정을 기록하는 곳에 (커밋 메시지, ADR, 이슈). main 브랜치에는 검증된 결정만 남는다.
