# UI 프로토타입

한 라우트 위에 **급진적으로 다른 UI 변형 여러 개**를 만들고, 플로팅 하단 바로 전환한다. 사용자는 브라우저에서 변형들을 넘겨 보고, 하나를 고르거나 (또는 각각에서 조각을 훔쳐서), 나머지를 버린다.

질문이 어떻게 생겼는가가 아니라 로직/상태에 관한 것이라면 — 분기가 틀렸다. [LOGIC.ko.md](LOGIC.ko.md) 를 쓴다.

## 이 형태가 맞는 경우

- "이 페이지가 어떻게 생겨야 하지?"
- "이 대시보드, 확정하기 전에 몇 가지 옵션을 보고 싶다."
- "설정 화면 레이아웃을 다르게 시도해 봐."
- 사용자가 머릿속의 흐릿한 목업 세 개 사이에서 하루를 허비할 뻔한 모든 경우.

## 두 하위 형태 — A 를 강하게 선호한다

UI 프로토타입은 **앱의 나머지와 맞닿아 있을 때** 훨씬 판단하기 쉽다 — 실제 헤더, 실제 사이드바, 실제 데이터, 실제 밀도. 단독 throwaway 라우트는 진공이다: 고립 속에서는 모든 변형이 괜찮아 보인다. 변형을 담을 그럴듯한 기존 페이지가 있는 한 하위 형태 A 를 기본으로 한다. 프로토타입이 정말로 깃들 곳이 없을 때만 하위 형태 B 로 간다.

### 하위 형태 A — 기존 페이지의 조정 (선호)

라우트가 이미 존재한다. 변형은 **같은 라우트 위에서** `?variant=` URL 검색 파라미터로 게이트되어 렌더링된다. 기존의 데이터 페칭, 파라미터, 인증은 전부 그대로 — 렌더링만 바뀐다. 이것이 기본값이다; 특별한 이유가 없는 한 이걸 고른다.

프로토타이핑 대상이 아직 페이지가 없지만 *자연스럽게 어떤 페이지 안에 살게 될* 것이라면 (대시보드의 새 섹션, 설정 화면의 새 카드, 기존 플로우의 새 단계) — 그것도 하위 형태 A 다. 변형을 호스트 페이지 안에 마운트한다.

### 하위 형태 B — 새 페이지 (최후 수단)

프로토타이핑 대상이 정말로 깃들 기존 페이지가 없을 때만 쓴다 — 예: 완전히 새로운 최상위 표면, 어디에도 합리적으로 끼워 넣을 수 없는 플로우.

프로젝트의 기존 라우팅 컨벤션을 따라 **throwaway 라우트**를 만든다 — 새 최상위 구조를 발명하지 않는다. 누가 봐도 프로토타입임이 드러나게 이름 짓는다 (예: 경로나 파일명에 `prototype` 을 포함). `?variant=` 패턴은 동일.

하위 형태 B 로 확정하기 전에 재확인: 정말 끼워 넣을 기존 페이지가 없나? 빈 라우트는 채워진 라우트라면 드러냈을 디자인 문제를 숨긴다.

두 하위 형태 모두에서 플로팅 하단 바는 동일하다.

## 절차

### 1. 질문을 명시하고 N 을 정한다

기본은 **변형 3개**. 5개를 넘으면 급진적으로 다르기를 멈추고 소음이 되기 시작한다 — 거기서 상한.

계획을 한 줄로, 프로토타입의 위치나 파일 상단 주석에 적는다:

> "설정 페이지 변형 3개, `?variant=` 로 전환, 기존 `/settings` 라우트 위에."

사용자가 반박하러 와 있든 아니든 이 방식은 작동한다.

### 2. 급진적으로 다른 변형을 생성한다

각 변형을 작성한다. 각각을 다음에 붙들어 맨다:

- 페이지의 목적과 접근 가능한 데이터.
- 프로젝트의 컴포넌트 라이브러리 / 스타일링 시스템 (TailwindCSS, shadcn, MUI, plain CSS, 무엇이든).
- 명확한 export 컴포넌트 이름, 예: `VariantA`, `VariantB`, `VariantC`.

변형은 **구조적으로 달라야** 한다 — 다른 레이아웃, 다른 정보 위계, 다른 주 어포던스. 색만 다른 게 아니라. 살짝 비튼 카드 그리드 세 개는 UI 프로토타입이 아니라 벽지다. 두 초안이 너무 비슷하게 나오면, "카드 그리드를 쓰지 마라" 같은 명시적 지침으로 하나를 다시 만든다.

### 3. 연결한다

라우트에 단일 스위처 컴포넌트를 만든다:

```tsx
// pseudo-code — adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

하위 형태 A (기존 페이지): 기존 데이터 페칭은 전부 스위처 위에 유지; 변형마다 렌더링되는 서브트리만 바뀐다.

하위 형태 B (새 페이지): `/prototype/<name>` 아래 throwaway 라우트가 같은 스위처를 마운트한다.

### 4. 플로팅 스위처를 만든다

화면 하단 중앙의 작은 fixed-position 바, 세 조각으로:

- **왼쪽 화살표** — 이전 변형으로 순환 (끝에서 감아 돈다).
- **변형 라벨** — 현재 변형 키를 보여주고, 변형이 이름을 export 하면 그것도. 예: `B — Sidebar layout`.
- **오른쪽 화살표** — 다음으로 순환 (감아 돈다).

동작:

- 화살표 클릭은 URL 검색 파라미터를 갱신한다 (프레임워크의 라우터를 쓴다 — Next 는 `router.replace`, React Router 는 `navigate` 등). 변형이 공유 가능하고 새로고침에도 안정적이도록.
- 키보드: `←` `→` 화살표 키로도 순환한다. `<input>`, `<textarea>`, `[contenteditable]` 에 포커스가 있을 때는 화살표 키를 가로채지 않는다.
- 페이지와 시각적으로 구분되게 (예: 고대비 pill, 옅은 그림자) — 평가 대상 디자인의 일부가 아님이 명백하도록.
- 프로덕션 빌드에서는 숨긴다 — `process.env.NODE_ENV !== 'production'` 이나 상당하는 체크로 게이트해서, 프로토타입이 실수로 머지돼도 바가 사용자에게 실리지 않게.

스위처는 공유 컴포넌트 하나에 두어 두 하위 형태가 재사용하게 한다. 프로젝트에서 공유 UI 가 사는 곳에 둔다.

### 5. 넘겨준다

URL 을 (그리고 `?variant=` 키들을) 알려준다. 사용자는 짬이 날 때 넘겨 볼 것이다. 흥미로운 피드백은 대개 **"B 의 헤더에 C 의 사이드바를 원해"** 다 — 그것이 사용자가 실제로 원하는 디자인이다.

### 6. 답을 캡처하고 정리한다

한 변형이 이겼으면, 답을 캡처하고 — 어느 변형이 왜 — 프로토타입은 [SKILL](SKILL.ko.md) 이 기술하는 방식으로 캡처한다. 승자를 실제 코드에 반영하고 나머지는 main 이 아니라 throwaway 브랜치로 옮긴다:

- **하위 형태 A** — 승자를 기존 페이지에 반영; 패배한 변형과 스위처는 main 에서 제거.
- **하위 형태 B** — 승리한 변형을 실제 라우트로 승격; throwaway 라우트와 스위처는 main 에서 제거.

변형 전체 세트가 1차 사료이므로 쓰레기통이 아니라 throwaway 브랜치에 싣는다 — main 브랜치에 남겨진 변형 컴포넌트와 스위처는 빠르게 썩고 다음 독자를 혼란시킨다.

## 안티패턴

- **색이나 문구만 다른 변형.** 그건 tweak 이지 프로토타입이 아니다. 진짜 변형은 구조에 대해 의견이 갈린다.
- **변형 간 코드 과공유.** 공유 `<Header>` 는 괜찮다; 공유 `<Layout>` 은 요점을 무너뜨린다. 각 변형은 레이아웃을 통째로 버릴 자유가 있어야 한다.
- **변형을 실제 mutation 에 연결.** 읽기 전용 프로토타입이면 충분하다. 변형이 mutation 을 필요로 하면 스텁을 가리키게 한다 — 질문은 "이게 어떻게 생겨야 하나" 이지 "백엔드가 작동하나" 가 아니다.
- **프로토타입을 프로덕션으로 직행 승격.** 변형 코드는 프로토타입 제약 (테스트 없음, 최소한의 에러 처리) 아래에서 작성됐다. 반영할 때는 제대로 다시 쓴다.
