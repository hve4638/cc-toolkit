# showcase

큰 코딩 작업을 `demo/` 아래의 데모들로 만들어, 사용자가 데모를 돌려보며 작업의 맥락을 따라가게 한다.

## 데모 분해

- 각 데모는 해소할 불확실성 하나로 정의한다 — 사람이 손으로 만들었다면 다음으로 확인했을 질문 (TUI 가 뜨긴 하는가, 실제 전송으로 A 의 메시지가 B 에 닿는가, 파싱된 레코드가 DB 에 적재되는가). 코드 구조의 단위로 정의하지 않는다.
- 순서는 사람이 손으로 만들며 확인하는 순서에서 끌어낸다: 일단 실행된다 → 구성 요소끼리 연결된다 → 데이터가 흐른다 → 실제 데이터로 교체된다 → 보기에 괜찮다 → 전체가 함께 동작한다. 프로젝트에 맞게 재배열하고, 독립적인 데모는 병렬로 진행해도 되며, 데모가 서로의 산출물 위에 쌓이면 의존 순서를 명시한다.
- 질문이 여러 구성 요소에 걸치면 데모를 수직 슬라이스로 자른다.
- 만들기 전에 데모 후보를 제시한다: 각각이 해소하는 질문과 실행하면 보일 것.

## 데모 산출물

- 각 데모는 `demo/<name>/` 자기 폴더에 두고, 단일 명령(예: `./run.sh`)으로 자체 실행 가능해야 한다; 폴더 자체가 시연이다.
- 데모의 핵심은 실물 — 제품 코드의 씨앗이다: 그 질문에 답하는 코드(전송 라이브러리, 프로토콜 배선, 파싱)는 제품에서 쓸 그대로 작성한다. 깡통·더미는 주변부(페이로드 내용물, UI, 출력만 하는 수신자)에만 둔다.
- 각 데모의 README 에 기록한다: 실행 명령, 관찰 포인트, 무엇이 깡통인지, 마지막으로 성공 실행된 커밋 해시.
- 데모는 코드가 진화해도 계속 동작하게 유지한다.

## 판정

- 데모는 기술·접근 채택의 판정 게이트가 될 수 있다. 데모가 후보의 부적합을 드러내면 README 에 판정과 사유를 기록하고 멈춘다 — 부적합 판정도 유효한 완료다. 우회 구현으로 얻은 통과는 README 에 그렇게 얻었다고 명시한다.

## 경계

- 데모 통과는 그것이 실행한 경로에 대한 증거일 뿐이다.
- 데모 폴더는 자체 검증의 일부로 자기 테스트를 품을 수 있다; 프로젝트 전체의 유닛테스트·CI·커버리지 정책은 별도 층에 맡긴다.
- 속도 조절은 사용자의 것이다: 데모가 실행 가능해지는 대로 제시하고 계속 진행한다; 멈춰서 관찰할 시점은 사용자가 정한다.
