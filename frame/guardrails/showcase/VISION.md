# showcase VISION

이 문서는 showcase 의 의도를 기록한다. 무엇을 만들려 했고, 왜 필요하며, 무엇은 일부러 하지 않기로 했는가. 구현이 진행되어도 갱신하지 않고 그대로 얼려 둔다. 나중에 나온 제안이 이 방향에서 벗어나거나 목적을 넘어설 때, 그 제안을 이 문서에 비춰 판단하기 위한 앵커다. 현재 진행 상태·규칙·계획은 다른 곳(PLAN, 스펙, 코드)에 있고, 여기에는 왜·무엇·무엇은 아닌지만 담는다. 이 판은 2026-07-05 의 체크포인트 재정의를 기록한 것이며, 이전 판(모듈 프레이밍)은 git 히스토리에 남아 있다.

## 무엇인가

showcase 는 큰 규모의 코딩 작업을 체크포인트의 시퀀스로 계획하고 진행하는 작업 규율이다. 체크포인트는 코드 구조의 단위가 아니라, 사람이 직접 만들었다면 그 시점에 눈으로 확인하고 싶었을 질문 하나다. TUI 가 뜨긴 하는지, 디바이스와 서버가 연결되는지, mock 데이터가 끝까지 흐르는지 같은 것이다. 각 체크포인트에 사용자가 직접 관찰할 수 있는 데모를 붙여, 낮은 인지부하로 "이건 됐다"를 확인하고 다음으로 넘어가게 한다. 확인이 쌓여 전체 시스템에 대한 신뢰로 이어진다.

체크포인트 시퀀스는 사람이 손으로 만들며 확인하는 순서를 따른다: 일단 실행된다, 구성 요소끼리 연결된다, mock 데이터가 흐른다, 실제 데이터로 교체된다, 보기에 괜찮다, 전체가 함께 동작한다. 질문이 여러 구성 요소에 걸치면 체크포인트는 수직 슬라이스가 된다. 모듈 경계와 일치할 필요가 없고, 구현 구조가 체크포인트 순서를 따를 필요도 없다. mock 과 stub 은 질문 하나를 분리해 보여주기 위한 일급 도구이며, 뒤 체크포인트에서 실물로 교체되고 필요하면 다시 도입된다.

데모는 확인이 끝나면 버리는 일회성 산출물이 아니라 코드와 함께 유지보수되는 요소다. 유지보수가 끊기는 경우에 대비해, 각 데모에는 동작을 확인한 커밋 해시를 기록해 둔다 (예: 데모·e2e 테스트 커밋 시 표기).

## 왜 / 목표

에이전트에 의존한 코딩의 산출물은 제대로 됐는지 표면만 보고는 신뢰하기 어렵다. 산출물이 클수록 더 그렇다. showcase 는 이 신뢰 격차를 사용자 쪽에서 메운다.

- 사용자가 직접 만들었다면 확인했을 것을 그 순서대로 대신 확인시킨다. 사용자는 안심하고, 진행에 대한 제어감을 유지한다.
- 각 체크포인트에 사용자가 직접 관찰할 수 있는 데모를 붙여, 설명이 아니라 확인으로 신뢰가 생기게 한다.

## 하지 않는 것

- 정확성 보증이 아니다. 데모를 통과했다는 것이 버그가 없다는 뜻은 아니다. 데모가 건드리지 않은 경로의 결함은 남을 수 있고, showcase 는 그것을 주장하지 않는다. 이것은 사람의 신뢰를 쌓는 층이지 기계적 정확성 증명이 아니다.
- 유닛테스트·CI·커버리지 정책에 관여하지 않는다. 기계 검증은 별도의 층이다. showcase 는 커버리지 수준을 강제하지 않는다.
- 구현 구조를 처방하지 않는다. 체크포인트는 사용자에게 확인을 제시하는 순서이지 코드를 조직하는 방식이 아니다. 구현이 체크포인트와 다른 구조·순서로 진행되어도 무방하다.
- inlay 를 대체하거나 그 위에 얹히지 않는다. inlay 는 에이전트에게 컨텍스트를 주는 내부용 층이고, showcase 는 사용자에게 확신을 주는 외부용 층이다. 체크포인트 경계도 inlay 의 INLAY.md 디렉토리 경계와 무관하다.
- 진행을 딱딱하게 막는 승인 게이트가 아니다. 기본은 체크포인트마다 멈춰 데모를 보이는 것이지만, 사용자가 연속 진행을 지시하면 멈추지 않는다. 속도는 사용자가 조절한다.
- 시각적 렌더링을 필수로 요구하지 않는다. 시각적 데모가 이상적이지만 본질은 관찰 가능성이다. UI 가 없는 체크포인트는 실행 가능한 데모 스크립트나 출력, e2e 로그처럼 사용자가 관찰할 수 있는 산출물이면 된다.

## 전제

- 사용자는 거대한 산출물의 표면을 훑어서는 신뢰를 형성하지 못한다. 신뢰는 자기가 확인하고 싶었던 질문의 답을 직접 관찰할 때 생긴다.
- 유닛테스트는 사람이 전체를 잘 들여다보지 않기 때문에 사용자 신뢰의 근거로는 약하다. 코드 단위의 e2e·데모도 사용자가 그 시점에 궁금해하던 질문과 어긋나면 확신을 주지 못한다. 확인의 단위는 코드가 아니라 질문이다.
- 체크포인트를 자르는 기준은 코드 구조가 아니라 "사용자가 다음으로 확인하고 싶은 질문"이다.
- 신뢰는 누적적이다. 순차는 에이전트가 사용자에게 확인을 제시하는 순서이지 구현 순서가 아니다.

## 시나리오

- 디바이스가 중앙 서버로 로그를 보내고 클라이언트 TUI 로 그 로그를 보는 시스템이라면: TUI 자체가 뜨는가 → 디바이스와 서버가 연결되는가 → mock 로그를 보내면 표시되는가 → 실제 연결에서 실제 로그가 뜨는가 → mock 응답으로 TUI 외관을 다듬으면 어떻게 보이는가 → 실제 데이터가 표시되는가. 이 순서로 체크포인트를 제시하고 각각을 데모로 보인다.
- UI 가 없는 체크포인트는 입력에서 출력까지를 보여주는 데모 스크립트나 e2e 로그로 관찰 가능성을 확보한다.
- 사용자가 "이번엔 데모를 일일이 보지 말고 끝까지 진행하라"고 하면, 데모는 산출물로 남겨 두되 진행은 멈추지 않는다.

## 열어 둔 것

- showcase 가 순수한 작업 규율에 머물지, 재사용 가능한 데모 스캐폴딩이나 도구까지 제공할지는 아직 정하지 않는다. 필요가 분명해질 때 정한다.
- 데모 산출물을 어디에 어떤 형식으로 남길지, 동작 확인 커밋 해시를 어떤 형식으로 표기할지에 대한 표준 규약 여부도 열어 둔다.
- 실물로 교체된 뒤의 mock 데모를 계속 유지할지 은퇴시킬지도 열어 둔다.
