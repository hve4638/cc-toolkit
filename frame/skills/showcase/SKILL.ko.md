# showcase

큰 코딩 작업을 사용자가 한 번에 이해하고 검증할 수 있는 모듈로 나누고, 각 모듈의 동작을 직접 관찰 가능하게 만든다.

## 모듈 분해

- 모듈 크기는 사용자가 한 자리에서 이해·검증할 수 있는가로 정하고, 코드 구조로 정하지 않는다.
- 모든 모듈은 그 경계에서 독립적으로 데모·테스트 가능하게 설계한다.
- 독립 데모가 안 되는 모듈은 진행 전에 선언한다: 코드에 불필요한 결합이 있거나 경계를 잘못 자른 것이다. 어느 쪽인지 지목하고 수정안을 제시한다.

## 모듈 루프

### Step 1 — 분해 제시

구현 전에 모듈 목록을 제시한다: 각 모듈의 범위와 데모가 무엇을 보여줄지.

### Step 2 — 모듈 하나 구현

경계에서 독립 실행 가능한 상태를 유지하며 모듈을 만든다.

### Step 3 — 데모 부착

사용자가 관찰할 수 있는 것을 만든다: 실행 가능한 데모 스크립트, e2e 출력, 시각적 렌더링. UI 없는 모듈은 데모 스크립트나 e2e 로그로 입력에서 출력까지 보여준다.

### Step 4 — 관찰용 제시

모듈 완료를 선언할 때 데모 산출물 경로, 실행 명령, 관찰 포인트를 함께 명시한다.

### Step 5 — 정지 또는 계속

데모를 제시한 뒤 멈춰 사용자가 관찰한 후 다음 모듈로 간다. 사용자가 연속 진행을 지시하면 멈추지 않되, 데모는 계속 만들어 산출물로 남긴다.

## 데모 산출물

- 데모는 코드와 함께 유지보수한다; 일회성 증명이 아니라 유지되는 산출물이다.
- 각 데모 산출물에 실행 명령과 마지막으로 성공 실행된 커밋 해시를 기록한다 (예: 데모·e2e 테스트 커밋 시 해시 표기).
- 산출물 위치·형식은 프로젝트별로 정한다; 위의 기록 정보만 필수다.

## 경계

- 데모 통과가 정확성을 보증하지 않는다; 데모가 건드리지 않은 경로의 결함은 남는다. 데모를 버그 없음의 증명으로 제시하지 않는다.
- 유닛테스트·CI·커버리지 정책은 별도 층이다. showcase 를 통해 커버리지 수준을 요구하지 않는다.
- 속도 조절은 사용자의 것이다; showcase 는 승인 게이트가 아니다.
