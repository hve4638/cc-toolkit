# showcase

큰 코딩 작업을 사용자가 관찰로 검증할 수 있는 체크포인트 시퀀스로 계획한다.

## 체크포인트 분해

- 각 체크포인트는 그 시점에 사용자가 눈으로 답을 확인하고 싶을 질문 하나로 정의한다 (TUI 가 뜨는가, 디바이스와 서버가 연결되는가, mock 데이터가 끝까지 흐르는가). 코드 구조의 단위로 정의하지 않는다.
- 시퀀스는 사람이 손으로 만들며 확인하는 순서에서 끌어낸다: 일단 실행된다 → 구성 요소끼리 연결된다 → mock 데이터가 흐른다 → 실제 데이터로 교체된다 → 보기에 괜찮다 → 전체가 함께 동작한다. 프로젝트에 맞게 재배열·교차하되, 각 체크포인트가 사용자가 다음으로 물을 질문에 답하게 유지한다.
- 질문이 여러 구성 요소에 걸치면 체크포인트를 수직 슬라이스로 자른다. 체크포인트는 모듈 경계와 일치할 필요가 없고, 구현 구조가 체크포인트 순서를 따를 필요도 없다.
- mock·stub 으로 체크포인트당 질문 하나를 분리한다. 데모가 mock 에 의존하면 무엇이 mock 인지, 어느 후속 체크포인트에서 실물로 교체되는지 명시한다. 실물로 교체된 뒤에도, 이후 체크포인트가 자기 질문을 분리하기 위해 mock 을 다시 들일 수 있다.
- 관찰 가능하게 만들 수 없는 체크포인트는 진행 전에 선언한다: 사용자가 확인할 것이 없는 항목이거나 (제거한다), 여러 질문이 묶인 것이다 (분할한다).

## 체크포인트 루프

### Step 1 — 시퀀스 제시

구현 전에 체크포인트 목록을 제시한다: 각 체크포인트가 답하는 질문과 데모가 무엇을 보여줄지.

### Step 2 — 체크포인트 하나를 향해 구현

현재 체크포인트를 관찰 가능하게 만드는 데 필요한 것을 만든다; 이후 관심사는 mock 뒤에 둔다.

### Step 3 — 데모 부착

사용자가 관찰할 수 있는 것을 만든다: 실행 가능한 데모 스크립트, e2e 출력, 시각적 렌더링. UI 없는 체크포인트는 데모 스크립트나 로그로 입력에서 출력까지 보여준다.

### Step 4 — 관찰용 제시

체크포인트 도달을 선언할 때 데모 산출물 경로, 실행 명령, 관찰 포인트, 아직 mock 인 부분을 함께 명시한다.

### Step 5 — 정지 또는 계속

데모를 제시한 뒤 멈춰 사용자가 관찰한 후 다음 체크포인트로 간다. 사용자가 연속 진행을 지시하면 멈추지 않되, 데모는 계속 만들어 산출물로 남긴다.

## 데모 산출물

- 데모는 코드가 진화해도 계속 동작하게 유지한다.
- 각 데모 산출물에 실행 명령과 마지막으로 성공 실행된 커밋 해시를 기록한다 (예: 데모·e2e 테스트 커밋 시 해시 표기).
- 산출물 위치·형식은 프로젝트별로 정한다; 위의 기록 정보만 필수다.

## 경계

- 데모 통과는 그것이 실행한 경로에 대한 증거로만 제시한다; 데모가 건드리지 않은 경로의 결함은 남는다.
- 유닛테스트·CI·커버리지 정책은 별도 층에 맡긴다.
- 속도 조절은 사용자의 것이다; showcase 는 승인 게이트가 아니다.
